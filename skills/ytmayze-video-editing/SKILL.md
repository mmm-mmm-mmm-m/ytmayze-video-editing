# @ytmayze Video Editing

This experimental kit grew from human rough cuts of Saint Alien and Cranky Glow, followed by many directed agent iterations. Its evidence concerns refinement of existing edits. It has not established reliable autonomous cutting from raw recordings or one-prompt finished tutorials.

Start from the creator’s rough cut when available. Use their time range, intended result, protected material and references to guide the pass. Drawings, screenshots, example clips, meme/audio assets and concrete feedback help communicate taste. Ask only for missing information that affects the result; make useful bounded progress with available direction. If asked to find missing assets, stay within the request’s sourcing permissions and track provenance. Keep a short passage reviewable before extending a treatment across the edit.

Make musical actions readable and leave room for patterns, silence and jokes to resolve. Adapt to the creator’s current direction instead of reproducing the source videos as a formula. If the request starts from raw footage, describe that as an untested use, agree on the editing scope and work in bounded drafts rather than promising a finished whole tutorial.

## Establish the pass

Use the current request and project to identify the target section, format, latest working version, and what may change. Separate structural editing from a finishing pass: “improve pacing” does not reopen approved cuts when the user has locked them. A research, review, or skill-building request does not authorize changes to videos. If editing is authorized, work in a named editable copy and preserve the original.

Inspect the local setup, action, musical event, reaction and return before treating a moment as weak. Read the existing project’s style notes or known-good examples before searching old chats. Reopen historical evidence only for a specific unresolved preference; do not re-mine the whole history on every edit.

For style mining or preset capture, check the current user-selected version before learning from screenshots or earlier drafts. Keep historical mechanism evidence separate from current layout/text/sound choices; a later correction can supersede a visually appealing old example.

## Check available capabilities

Identify the editor, accessible project/media and available playback/render tools. The principles transfer across editors; native project formats and automation commands do not. If execution is unavailable, deliver a cue list or editing specification and state what requires an editor. Never present a specification or a rendered file as an edit applied to the host project. No source footage, meme media, sound library, fonts or native presets are bundled.

## Choose the useful skills

Load only the skills needed for the pass, if available. The public kit contains all eight; if a companion is missing, use available guidance and identify any missing specialist workflow:

| Need | Skill |
| --- | --- |
| Readable notes, mouse/playhead tracking, camera placement or vertical layout | `$ytmayze-frame-daw` |
| Flat moments, phrase lengths, action progression or reveal timing | `$ytmayze-pace-music` |
| Kick/bass pumps, slides, synchronized glow, distortion or motion | `$ytmayze-reactive-vfx` |
| Foley, transitions, meme audio, dialogue balance or mix protection | `$ytmayze-design-sound` |
| Contextual jokes, captions, lyric typography or CTA presentation | `$ytmayze-engagement` |
| Editable animated insert or reference adaptation with HyperFrames | `$ytmayze-hyperframes-inserts` plus the installed HyperFrames skill |
| Save, inspect or adapt a reusable effect/layout or laptop shortcut composite | `$ytmayze-effect-presets` |

A focused request can be completed directly. For a broad pass, use a small cue list: moment, viewer problem, proposed treatment, event anchor, protected material, and review needed. Prioritize corrections that make the action understandable before increasing spectacle. Avoid unrelated cleanup or adding every available treatment to each moment. Use the creator’s chosen editor and workflow; these skills do not require another general video-editing skill.

## Style judgment

- Let the listener hear the pattern, sound change, or first full beat. Low cut density can be purposeful. Build visual energy around playback when it benefits the moment.
- Let comedy come from the creator’s delivery, musical event, and context. Dry silence, clean framing, a restrained zoom, or one decisive accent can be stronger than a stack of memes. Ambitious absurdity is welcome when setup and payoff carry it.
- Treat a reaction as performance worth shaping, not something to hide automatically. Avoid intense wiggle that makes awkward body language more conspicuous.
- Keep motion, text, source action and audio telling the same story. If two elements compete, decide which one the viewer should follow.
- Current explicit direction wins over these defaults. A treatment rejected for the current scene stays rejected even if a render succeeded. A suggested sound, specific meme, scene duration or old offer is not an enduring preference.

## Preserve and verify

For EffectCraft project changes, read [edit integrity](references/edit-integrity.md). Keep ordinary picture, camera, sound and effects accessible; use precomps when a composite actually benefits. Do not lock layers as an organizing shortcut. Avoid cleanup of uncertain/hidden assets unless requested.

Verify at the scale of the change: compare the intended property changes and protected timing/audio, then watch the affected passage continuously with its lead-in and return. Frame snapshots catch composition; playback catches motion; listening catches mix and comic timing. State which checks actually happened. Technical success, an inspected preview, and user creative acceptance are separate facts. If audio/video review is unavailable, label it pending.

Deliver the editable result and a concise account of what changed, what was verified, and any unresolved creative choice. Do not insert a new approval stop when the user has already authorized execution/rendering; respect explicit requests for a mock, storyboard, or preview first.

## Keep developing the style

When the user asks to update this kit, turn concrete feedback into a narrow correction or example in the owning skill. Record the context and evidence; distinguish a repeated preference from a local experiment. Keep rejected examples as useful boundaries without banning an entire technique. The [project style note](references/project-style-note.md) is an optional compact handoff for substantial ongoing edits, not paperwork for every small change.
